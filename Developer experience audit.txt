## 1. Getting Started / Onboarding

### Build System: A Hard Gate

The single biggest onboarding obstacle is the **Zig-only build system**. The target audience overwhelmingly uses CMake, Make, or just compiles with raw `gcc`/`clang` commands. Requiring Zig 0.15.2 means:

- Installing a specific version of a niche toolchain they almost certainly don't have
- Learning enough Zig build semantics to troubleshoot if anything goes wrong
- No way to integrate Bandura into their existing `CMakeLists.txt` or `Makefile`

There is no `CMakeLists.txt`, no `Makefile`, no `pkg-config` file, no vcpkg/conan manifest. The `Justfile` contains a single `release` recipe — helpful only if you already have both `just` and `zig` installed.

For a hobbyist who wants to "add physics this weekend," the realistic path is:

1. Install Zig 0.15.2 (hope it's available for their platform/package manager)
2. Run `zig build --release=fast -Dinclude-demos=false`
3. Find the `.so`/`.dll` and two headers in `zig-out/`
4. Manually copy them into their project
5. Figure out linker flags themselves

There are no prebuilt binaries. There is no CI pipeline that could even produce them. This is a significant amount of friction before writing a single line of physics code.

**Verdict:** High friction. Many hobbyists will bounce here.

### Quickstart Documentation

The README does include a quickstart section, which is good. However, the path from "I have the source" to "physics is running in my game" requires mentally stitching together several README sections: build instructions, quickstart code, and framework-specific integration (e.g., the Raylib mesh example). There is no single, end-to-end "here's a complete 50-line program" that compiles and runs.

## 2. API Design & Ergonomics

### The `bnd_body` Pointer Pattern

This is the most architecturally unusual decision in the API and the one most likely to cause silent bugs:

```c
bnd_body body = bnd_add_body(...);
// body.position, body.rotation, etc. are raw pointers
// into internal engine memory

*body.position = (bnd_v3){0, 10, 0};  // OK here

bnd_simulate(world, dt);

*body.position = (bnd_v3){0, 20, 0};  // UNDEFINED — pointer may be invalid
```

The library hands you raw pointers that are **silently invalidated** by `bnd_simulate`. There is no compile-time or runtime protection. A hobbyist who stores `bnd_body` in a struct and writes to it next frame will get memory corruption with no error message. This is a dangling-pointer footgun aimed directly at the audience least equipped to diagnose it.

The *intended* workflow is: use `bnd_body` immediately after creation for initial setup, then switch to `bnd_body_handle` for everything else. But this two-phase pattern is non-obvious and easy to get wrong. There are getters (`bnd_get_position`, `bnd_get_velocity`) but **no setters** — the only way to set position is through those ephemeral raw pointers. This means you literally cannot teleport a body after the frame it was created.

**This is the single most dangerous API decision for this audience.**

### Getter/Setter Asymmetry

| Operation | Initial Setup | After Simulation |
|---|---|---|
| Set position | `*body.position = ...` | **Impossible** |
| Get position | `*body.position` | `bnd_get_position(handle)` |
| Set velocity | `*body.velocity = ...` | **Impossible** |
| Get velocity | `*body.velocity` | `bnd_get_velocity(handle)` |

For a game developer, not being able to set a body's position at an arbitrary time is a severe limitation from an ergonomics standpoint. Teleporting entities, resetting state, implementing respawns — all are common operations that this API simply doesn't support after creation.

### Configuration Complexity

## 2. API Design & Production Readiness

### 2.1 The `bnd_body` Immediate-Use Pointer Pattern

**Rating: Poor — this is the most serious API design issue**

`bnd_body` (defined at `bandura.h:144-151`) returns raw pointers into internal SoA arrays:

```c
typedef struct {
  bnd_v3 *position;
  bnd_quat *rotation;
  bnd_v3 *velocity;
  bnd_v3 *angular_momentum;
  bnd_body_handle handle;
} bnd_body;
```

These pointers are **invalidated by any subsequent body addition or removal** (due to reallocation in `realloc_data` at `world.c:360-395` and swapping in `swap_bodies` at `world.c:1100-1143`). The README notes this at line 115, but the API provides no compile-time or runtime guard against dangling use.

This pattern is dangerous in any codebase larger than a demo. If a studio engineer adds two bodies in sequence:

```c
bnd_body a = bnd_add_sphere_dynamic(world, 5, 1);
bnd_body b = bnd_add_sphere_dynamic(world, 5, 1);
*a.position = vec3(0, 5, 0); // POTENTIAL USE-AFTER-FREE
```

The second `bnd_add_*` call may realloc the positions array, invalidating `a.position`. This is **undefined behavior** with no diagnostic. The README warns about `bnd_simulate` invalidating pointers, but the actual danger zone is **any subsequent body creation**, which the README does not explicitly call out.

### 2.2 Getter/Setter Asymmetry

**Rating: Poor**

There are getter functions (`bnd_get_position`, `bnd_get_velocity`, etc.) but **no setter functions**. The only way to set a body's position is through the `bnd_body` raw pointers at creation time. After that first simulation step, there is no public API to teleport, reposition, or reset a body's transform.

This makes the library unusable for common game scenarios:
- Respawning a player
- Teleporting entities
- Level transitions
- Serialization/deserialization of world state
- Editor "move object" tools
- Networking: applying server-authoritative corrections

This is not a minor omission — it is a **fundamental missing capability** for game development.

### 2.3 Handle Consistency

Bodies use `bnd_body_handle` (a typed struct with generational index), which is good. But joints use `count_t` (i.e., `uint32_t`) as their ID type (`bandura.h:261-263`). This means:

- No type safety between body handles and joint IDs — both are ultimately `uint32_t`
- No generational validity checking for joints
- Joint IDs could be accidentally passed where body handles are expected (different parameter types help, but the inconsistency signals an unfinished API)

### 2.4 Namespace Pollution

`typedef uint32_t count_t;` at `bandura.h:33` defines a **global, unqualified typedef** in the public header. Any consumer project that defines its own `count_t` will get a compilation error. This should be `bnd_count_t` or removed entirely in favor of `uint32_t`.

Similarly, `bnd-math.h` defines:
- `EPSILON` at line 7 — an extremely common macro name, guaranteed to collide
- `vec3(x,y,z)` and `quat(x,y,z,w)` at lines 10-11 — short macro names with high collision probability

The header itself has a TODO to remove `vec3`/`quat` (line 9), acknowledging the problem.

### 2.5 Missing User-Data Attachment

There is no `void *user_data` field on body handles or any `bnd_set_user_data` / `bnd_get_user_data` function. Every physics engine used in games needs this. Without it, studios must maintain a parallel lookup table mapping `bnd_body_handle` to their own game object, which is error-prone and slower than a simple pointer stored alongside the body.

### 2.6 Thread Safety

There is **zero documentation** about thread safety. The API uses a global `error_callback` function pointer (`core.c:18`) and a global `error_message_buffer` (`core.c:17`). If two threads call any function that raises an error simultaneously, the error message will be corrupted (race condition on `error_message_buffer`). The error callback itself is global, not per-world — problematic for multi-world scenarios.

For a professional studio running physics on a dedicated thread (standard practice), the lack of any threading documentation or guarantees is a significant risk.

## 3. Memory Management & Control

### 3.1 Custom Allocator Design

**Rating: Good (with caveats)**

The `bnd_allocator` struct (`bandura.h:74-78`) is well-designed for the target audience:
- `malloc` takes alignment and size (alignment-aware allocation is essential for SIMD/cache-line work)

- `free` is optional (good for arenas that free all at once)
- `realloc` passes both old and new sizes (excellent — this is what arena/pool allocators need)

## 4. Error Handling & Reliability

### 4.1 Error Reporting Model

**Rating: Below Average**

The library has two error reporting mechanisms that don't compose well:

1. **Return-value errors** — `bnd_init_with_allocator` returns `bnd_error`, `bnd_import_mesh` returns `bnd_error`
2. **Global callback** — `bnd_register_error_callback` sets a single process-wide function pointer

Problems:
- Body creation functions (`bnd_add_*`) return `bnd_body` with no error channel. On failure, they return `INVALID_BODY` (all-null pointers, `INVALID_INDEX` handle). The only way to detect failure is checking `bnd_handle_valid()` on the result — but the README example at line 504 calls `bnd_handle_valid()` **with no arguments**, which is a compilation error.
- The global error callback writes to a single static buffer (`error_message_buffer`, `core.c:17`). If the callback is invoked from multiple contexts (or re-entrantly), messages are corrupted.
- If no callback is registered, errors are **silently dropped** (`core.c:293-295`). Applying force to an invalid handle with no callback registered produces zero feedback.

### 4.2 Specific Reliability Concerns

- `bnd_v3_normalize` in `bnd-math.h:33-38` has an empty `if` body when the vector length is below `EPSILON`. This is almost certainly a missing assertion or error path.
- `bnd_init` at `core.c:222-228` does not propagate allocation failures to the caller.
- `bnd_awaken_body` at `world.c:1059-1080` calls `handle_to_inner_index` **before** validating the handle (`bnd_handle_valid` check is at line 1068, but `handle_to_inner_index` is at line 1063). This can produce an out-of-bounds array access on an invalid handle.

## 6. Binding Generation & Ecosystem

### 6.1 FFI Friendliness

**Rating: Average**

Positive signals:
- `bnd_world` is an opaque pointer type (`bandura.h:215`) — ideal for FFI
- Most functions take/return simple structs and handles — straightforward to marshal
- No C++ features in the public API
- Generational handle pattern maps well to FFI (it's just a struct of integers)

### 6.2 FFI Obstacles

- **Anonymous unions** in `bnd_body_shape` (`bandura.h:102-121`) and `bnd_event` (`bandura.h:227-231`) — these are not representable in many FFI systems (C#'s P/Invoke requires `[FieldOffset]` attributes with explicit layout; GDScript has no union support at all)
- **Function pointer callbacks** (`bnd_error_callback`) require careful lifetime management in managed languages
- **The `bnd_body` raw pointer pattern** cannot be safely exposed through FFI — managed languages cannot safely dereference C pointers that may be invalidated by future calls
- **`count_t` typedef** — binding generators will see `uint32_t`, losing the semantic meaning
- **No `extern "C"` guard** — the header will work when included from C but requires the consumer to add `extern "C"` when used from C++. A standard `#ifdef __cplusplus extern "C" {` block is expected.
- **No static library option** — only dynamic library output (`build.zig:138`). Many engines (especially mobile targets) prefer static linking.

## 7. Overall Verdict

### Strengths

1. **Clean opaque world type** — `bnd_world*` is correctly hidden, preventing consumers from depending on internal layout
2. **Custom allocator with alignment support** — well-designed for game engine memory systems, with `bnd_required_memory` for pre-allocation
3. **Data-oriented internal architecture** — SoA layout, bracket-based collision grouping, and separation of hot/cold data suggest good cache behavior (though this is a performance attribute, the clean internal structure makes the codebase easier to audit)
4. **Small, self-contained codebase** — 14 source files, no dependencies, compiles with standard C warnings enabled

### Weaknesses

1. **No standard build system integration** — Zig-only build is a hard blocker for most studios
2. **Dangerous `bnd_body` raw pointer pattern** — trivially produces use-after-free with no diagnostic
3. **No setter functions** — cannot reposition bodies after creation, making the library unsuitable for most game scenarios
4. **No Windows `dllimport`** — broken shared library consumption on Windows
5. **Global mutable state** (error callback, error message buffer) — not thread-safe, not multi-world safe
6. **Near-zero test coverage** — 3 test functions for an entire physics engine
7. **No API reference, no changelog, no versioning policy**
8. **Namespace pollution** (`count_t`, `EPSILON`, `vec3`, `quat`)
9. **No user-data field on bodies**
10. **C11 features in a nominally C99 header**

### Rating: **Below Average**

Bandura shows competent physics engineering internally (the SoA layout, GJK/EPA implementation, generational handles, bracket system). But from a **professional integration standpoint**, it is not ready for production use. The build system gap alone disqualifies it from most studios' evaluation processes, and the API-level issues (no setters, unsafe pointer pattern, no thread safety) would be discovered in the first hour of integration and likely end the evaluation.

2. **Add `bnd_set_position`, `bnd_set_velocity`, `bnd_set_rotation`, `bnd_set_angular_momentum` functions — and deprecate the raw-pointer `bnd_body` pattern.** The setter functions should take `(bnd_world*, bnd_body_handle, value)` and be safe to call at any time. # Bandura Physics Engine — Developer Experience Audit

## Group 1: Hobbyist Game Developers (Raylib / SDL)

### Getting Started / Onboarding

The single biggest barrier is the **Zig-only build system**. This audience overwhelmingly uses CMake, Make, or raw `gcc`/`clang`. Requiring Zig 0.15.2 (a niche toolchain in a non-stable version) means installing unfamiliar tools before writing a single line of physics code. There are no prebuilt binaries, no CMakeLists.txt, no Makefile, no pkg-config, and no CI pipeline that could produce release artifacts. Many hobbyists will bounce here.

The README does include a quickstart, but there's no single end-to-end compilable example file that a user can `gcc example.c -lbandura -o example` to verify their setup.

### API Design & Ergonomics

**The `bnd_body` pointer pattern is the most dangerous design decision for this audience.** Body creation returns raw pointers into internal engine memory (`bnd_v3 *position`, etc.) that are silently invalidated by `bnd_simulate` *and by any subsequent body creation* (due to potential reallocation). A hobbyist who stores `bnd_body` and writes to it next frame gets memory corruption with zero error message.

Compounding this: **there are no setter functions**. The only way to set a body's position is through those ephemeral raw pointers at creation time. After that, you have `bnd_get_position` but no `bnd_set_position`. Teleporting entities, respawning, resetting state — all impossible after the creation frame.

Other concerns:
- `count_t` typedef adds confusion vs standard `uint32_t`
- Joint IDs are bare `uint32_t` while bodies get typed generational handles — inconsistent safety
- `bnd_config` exposes 20+ tuning parameters including internals like `epa_max_nodes` and `shapes_brackets_capacity[5]`

**Bright spot:** The `BND_CUSTOM_VEC3`/`QUAT`/`MAT3` overrides are genuinely good — letting Bandura use Raylib's `Vector3` directly eliminates conversion boilerplate.

### Documentation

Two confirmed bugs in README examples that will fail to compile:
- `bnd_body_shape shapes[] = {}` (invalid C99 syntax, `README.md:140`)
- `bnd_handle_valid()` called with no arguments (`README.md:504`)

Coverage of workflows (spawning, joints, meshes, events, raycasts) is solid, and the Raylib-specific examples are well-targeted. But there's no API reference, no explanation of what config parameters do, no discussion of timestep management, and no troubleshooting section.

### Verdict: **Below Average**

**Top 3 improvements:**
1. Add a CMakeLists.txt or publish prebuilt binaries — eliminate the Zig requirement
2. Add setter functions (`bnd_set_position`, `bnd_set_velocity`, etc.) to replace the raw-pointer pattern
3. Fix documentation bugs and provide a complete, compilable example file

## Group 2: Professional Studios (Unity / Godot / Custom Engines)

### Build System & Platform Support

The Zig-only build system is a **hard blocker** for professional pipelines. No CMake, Meson, pkg-config, vcpkg, or Conan support. Studios cannot `find_package(Bandura)` or integrate it into any standard build workflow.

Windows support is declared as "should work but is not actively tested" — and the `BNDAPI` macro has a **shipping bug**: it defines `__declspec(dllexport)` but never `__declspec(dllimport)`, meaning Windows consumers linking against the DLL will get linker errors.

The header claims C99 but uses anonymous unions (`bnd_body_shape`, `bnd_event`) — a C11 feature that will fail under strict C99 compilers. No `extern "C"` guard for C++ consumers.

### API Design & Production Readiness

**Critical issues:**

| Problem | Impact |
|---|---|
| No setter functions after creation | Cannot teleport, respawn, serialize, or network-correct body positions |
| `bnd_body` raw pointers silently invalidated | Use-after-free with no diagnostic, even between consecutive body additions |
| Global error callback + static message buffer | Not thread-safe, not multi-world safe |
| No `void *user_data` on bodies | Studios must maintain parallel lookup tables |
| `count_t` / `EPSILON` / `vec3` / `quat` in global namespace | Collision risk in large codebases |
| No `extern "C"` block | Requires manual wrapping for C++ |

**Positive aspects:**
- `bnd_world*` is properly opaque
- Generational handle pattern on bodies is correct
- Custom allocator with alignment support and `bnd_required_memory` is well-designed
- Small, self-contained codebase (14 source files, no deps) is easy to audit

### Documentation & Quality Signals

No API reference, no Doxygen, no changelog, no versioning policy, no migration guide. Version is `0.0.1`. The test suite has 3 test functions covering profiler labels, CSV monitor, and shapes — no tests for body lifecycle, collision detection, handle validity, joints, events, allocator paths, or error handling. No CI pipeline running on any platform.

### FFI / Binding Generation

Anonymous unions in `bnd_body_shape` and `bnd_event` are difficult to represent in C# P/Invoke and impossible in GDScript. The `bnd_body` raw-pointer pattern cannot be safely exposed through any managed-language FFI. Only dynamic library output is available (no static linking option).

### Verdict: **Below Average**

The internal engineering (SoA layout, GJK/EPA, bracket system) signals competence, but the API surface is not production-ready.

**Top 3 improvements:**
1. Add CMake support + fix Windows `dllimport`/`dllexport` — this is the highest-leverage change
2. Add setter functions and deprecate the raw-pointer `bnd_body` pattern; add `user_data` on bodies
3. Add a real test suite and CI pipeline (Linux/macOS/Windows) — minimum bar for professional trust
